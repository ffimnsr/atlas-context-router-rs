## Predicted

Test 35.1 expects details.governing_threshold to name the triggering threshold and details.threshold_kind to be `cyclomatic` when complexity_threshold=15 selects the finding.

## Actual

With complexity_threshold=15 every candidate reports governing_threshold=80 and threshold_kind="loc" (e.g. execute_graph_operation cyc=32, run_memory cyc=41, update_graph cyc=63). In the file-scoped run (35.3) the value flips per row: select_graph_health_error_code has threshold_kind="cyclomatic_complexity" while looks_like_missing_graph_db has "loc", and candidate.threshold stays 80 while governing_threshold is 5. `details` is omitted entirely in compact mode (details_omitted=true).

## Correction

governing threshold selection in rank_large_function_candidates/candidate_to_finding is loc-first and mode-blind for the `complex` path, and the emitted metric token is `cyclomatic_complexity` while the contract says `cyclomatic`. Fix: make governing_threshold/threshold_kind reflect the metric actually gated by the request (complexity_threshold/cognitive_threshold) when mode=complex, normalize the token to `cyclomatic`, and keep governing_threshold consistent with candidate.threshold. Same defect reproduces through CLI `atlas insights complex-functions --complexity-threshold 15`, so MCP/CLI parity is intact.
