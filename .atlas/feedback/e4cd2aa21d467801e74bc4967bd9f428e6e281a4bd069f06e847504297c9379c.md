## Predicted

Tests 50.1/50.3: mark_consumed=false leaves the snapshot pending, and resume rebuilds a snapshot on demand when no pending snapshot exists.

## Actual

live session: resume_session(mark_consumed=false) returned snapshot_status=existing_snapshot with created_at 2026-11-12, event_count 24 while the session had 40+ events; get_session_status simultaneously reported resume_snapshot_exists=false, snapshot_consumed=true. On-demand rebuild never runs when a consumed session_resume row exists (session.db session_resume row: consumed=1, event_count=24, created_at 2026-11-12). A brand-new session id does rebuild (snapshot_status=built_snapshot).

## Correction

resume_snapshot_exists is derived from the consumed flag, but the resume read path returns the stale persisted snapshot instead of treating a consumed row as absent and rebuilding from recent events (packages/atlas-session/src/store/resume.rs build_resume_snapshot / get_resume_snapshot). Fix: rebuild when consumed=true (or refresh the stored snapshot on read), so status.exists=false and resume's returned snapshot stay consistent; test 50.1/50.3 expectations otherwise cannot both hold.
